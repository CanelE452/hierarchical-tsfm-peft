# 최종 대표 checkpoint replay 준비: 실제 29 PASS와 신규 후보 구분

이 문서는 T를 보지 않고 작성한 실행 준비다. 선택 잠금·새 replay·T 평가 완료가 아니다. 공개 MASTER §15.4의 [519행](../../../plan/MASTER_PLAN_PUBLIC.md#154-checkpoint-재추론), 원본 MASTER의 517행은 자료별 최종 Raw/G/B0/제안/LoRA의 고정 V origin 실제 replay를 요구한다. 접근 가능한 main4 × 다섯 비교 역할은 최소 20개 경로가 된다. `20`은 본문에 독립적으로 명시된 숫자가 아니라 이 요구를 main4에 적용한 산술이다. 첫·중간·마지막 및 고정 난수 origin의 subset 재추론이며 전체 재학습·전체 V 재추론이 아니다.

이번 구체 후보의 제안 역할은 같은 deep G의 `B2 conditional H`다. 학습 endpoint가 같은 B2 부모 자체 4개도 지원 목록에 보존했다. 이 구분은 B2 부모만의 결과와 H 결합 결과를 섞지 않기 위한 것이다. 자동 성능 순위나 T 결과로 고르지 않았다. 최종 ID 선정은 ROOT가 V·비용·실제 자원을 검토하고 별도로 잠근다.

## 확정 입력 목록과 기존 PASS

- [REPLAY_CORE20.json](../../gzip_aux95_1792094747124151400/files/item_0075.json.gz): RawSmall/G/B0/B2-H/LoRA × main4, 명시적 20개 ID.
- [REPLAY_MATCHED_FULL40.json](../../gzip_aux95_1792094747124151400/files/item_0074.json.gz): 위 20개와 B2 부모/B0-H/Raw-H/동용량 과거 H/전역 alpha × main4의 20개 지원 경로. 같은 sealed deep G를 쓰는 조건을 보존한다.
- [CANDIDATES40.csv](../../gzip_extra_aux_20261016_v1/files/item_0413.csv.gz): 정확한 ID, manifest SHA, 현 registry 상태, 학습 endpoint/선택 상태, 비교 역할과 원 V 수치.
- [EXISTING_PASS29.json](../../gzip_extra_aux_20261016_v1/files/item_0415.json.gz): 실제 저장 replay 영수증 29개의 exact ID·SHA·선택 artifact binding·현재 표준 V manifest SHA를 대조했다.

core20과 기존29의 exact 교집합은 세 개다: Electricity RawSmall, PeMS08 RawSmall, PeMS08 초기 LoRA. 따라서 core20은 기존 3개와 신규 17개, full40은 기존 3개와 신규 37개다. 그 외 기존26개의 PASS는 다른 ID/부모/체크포인트이므로 새 모델을 대신 검증하지 않는다. 새 bundle의 가중치가 과거와 같다는 메타데이터 관찰만으로 replay PASS를 이전하지 않는다. 같은 ID의 기존 PASS도 ROOT 실행 API가 현재 portable route hash와 artifact 계약을 다시 대조해야 재사용할 수 있다. 이 작업에서는 route 객체·weights를 열어 그 마지막 단계를 실행하지 않았다.

Beijing G/B0/B2는 실제 3epoch 탐색 완료 후 선택 checkpoint의 A60 refit이다. 다른 세 자료의 비교 부모는 sealed E2의 1epoch 경로다. Beijing LoRA는 별도 `__e3`이고 다른 세 자료의 LoRA는 `PARTIAL_SCREEN025 / LIMITED_SCREEN`이다. 실제 BASE와 V가 있어 replay 후보로 남겼지만, 그 세 LoRA를 3epoch 완료로 세지 않는다. 조건별 학습량·선택 지점·정보량이 다르므로 최선 방법 비교와 순수 P 효과 또는 동일 튜닝 예산을 구분한다. H의 3epoch 완료도 선택 마지막 지점·clipping·미수렴 상태를 그대로 남긴다.

core20/full40은 모든 원리의 T를 자동 결정하는 목록이 아니다. [PRINCIPLE_AND_STRONG_BASELINE_CANDIDATES.csv](../../gzip_extra_aux_20261016_v1/files/item_0417.csv.gz)는 E3/E4와 native/강한 기준선의 현존 후보 및 새 E4 미완료를 별도로 남긴다. 어떤 원리가 나쁜 점수라는 이유로 통째로 생략하도록 권고하지 않는다. 실제 선택될 추가 경로는 그 exact ID의 replay·감사·비용을 별도로 확인해야 한다. 새로운 E4 `__e3` 두 parent는 BASE/V가 없어 후보 실행에 넣지 않는다. 기존 초기 E4 checkpoint는 그 미완료 새 시도와 구분한다.

## 실제 Raw+deep G 종료 검토

[RAW4_CLOSURE_REVIEW.json](../../gzip_extra_aux_20261016_v1/files/item_0418.json.gz)은 Raw H4의 실제 receipt/V manifest SHA, 현존 source33, 새 4행과 Raw parent 과학 identity, 중앙 closed lease와 GPU_USAGE 단일 exact 장부를 읽기 전용으로 대조했다. 실제 H 네 개는 모두 3epoch, 업데이트 388/386/448/334, H 학습 F 호출0이다. 학습의 F0를 Raw 배포의 F0로 해석하지 않는다. GPU 장부는 CLOSED·141.37190651893616초·deadline overrun0이며 runtime PID58964가 조회 시점에 없음을 별도 OS 조회로 확인했다. exit0는 ROOT가 실제 종료를 관찰한 기록으로 인계받았고 여기서 프로세스를 재실행하지 않았다.

전체 old registry 행 불변은 원 worker의 시작/종료 대조 결과 `scientific_rows_unchanged=true`, `unexpected_mutable_changed_ids=[]` 및 ROOT 사전등록 증거를 참조한다. 이번 독립 검토가 저장되지 않은 과거 전체 registry bytes를 새로 복원했다고 주장하지 않는다. FP64 재채점과 같은 G의 성능 비교는 다른 담당자가 수행하므로 중복하지 않았다.

## ROOT 전용 작은 replay 실행기

private `final_execution/final_replay_explicit_1792091200000000000.py`는 개인 절대경로 상수 없이 `INFORMS_PUBLIC_ROOT`, `INFORMS_CACHE_ROOT`, `INFORMS_ASSET_ROOT`만 읽는다. [AST와 실제 metadata 실행 증거](../../../diagnostics/final_replay_readiness_1792091200000000000_v3/WRAPPER_AST_AND_METADATA_PROOF.json)는 core20/full40 모두 exit0·numpy/torch/pandas import0을 확인한다. 체크포인트는 선언된 SHA와 파일 존재를 준비 단계에서 묶었고 모델 객체/NPZ/weights는 로드하지 않았다.

기본 명령은 `python -X utf8 -B <private wrapper> --plan-json <REPLAY_CORE20.json 또는 REPLAY_MATCHED_FULL40.json의 로컬 절대경로>`다. ROOT가 원본 코드를 검토하고 비용 owner와 이전 작업의 종료를 확인한 뒤에만 `--execute`를 추가한다. 환경 GPU는0, CPU threads는2다. ACTIVE GPU lease나 상속 owner가 있으면 새 실행을 거부한다.

실행은 기존 GPUReservation `purpose=audit,total_gpu_seconds=43200,reserve_seconds=0,wall_deadline=1792223150` 안에서 `final_evaluation.execute_replays`만 호출한다. 새 ID를 고르거나 `lock_selection`, `execute_T`, Git, registry 변경을 호출하지 않는다. 실제 API가 경로별 실패·reuse·잔여 deferred를 보존한다. 기존 source18은 실행 직전과 종료에 대조하며, 새 wrapper가 기존 CPU421 또는 기존 전체 source 검증에 포함된 것처럼 쓰지 않는다.

기존 FINAL_EVALUATION_PROTOCOL의 API 열거는 lock을 먼저 나열하지만 실제 source `final_evaluation.py:284,352`는 `final=False` V replay에 lock을 요구하지 않는다. 최신 FINAL_SELECTION_RULE은 선택 후보 replay PASS를 잠금 전에 확인하도록 명시한다. 따라서 ROOT의 실제 순서는 비용 종료 → exact 후보 V replay → 선택 전 독립 감사 → 명시적 lock → 공식 execute_T다. 이 문서는 T 접근을 허가하거나 실행하지 않는다.

이후 새 산출물은 FINAL DELTA다. [CAPTURE.json](../../gzip_extra_aux_20261016_v1/files/item_0414.json.gz)의 cutoff·입력 SHA를 기준으로 읽으며 이 스냅샷을 최종 전체 평가나 충분 학습 완료로 부르지 않는다. 준비 중 alpha-family가 별도 head checkpoint를 갖지 않는다는 API 차이와 초기 LoRA의 PARTIAL 상태를 확인해 입력을 교정했으며, 먼저 생성된 부분 준비 폴더 두 개는 원본 보존하되 최종 근거로 쓰지 않는다.

SHA256은 `8dee2e5a902a17535962f28ae7a06a8675b29dbadb16357d0a341e4b5bf61e30`으로 동일하다. 사용자 절대경로를 포함하지 않고 위 세 환경변수로 자산·캐시·공개 루트를 받는다. 기본 metadata 동작과 명시 `--execute` 동작은 동일하다. 복사 자체는 GPU 실행이나 새 replay PASS의 증거가 아니며 실제 실행 결과는 후속 ROOT execution receipt를 따른다. 이 보충 이전에 봉인한 FINAL_ARTIFACTS_SHA256.json은 당시 파일을 대상으로 하므로 새 코드·본 README 수정은 최종 게시 증분에서 별도로 검사한다.
