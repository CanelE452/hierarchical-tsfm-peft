# 최종 게시 공간 — 메타데이터 단계 검토

이 문서는 기존 후보 4,600파일을 변경하지 않은 공간 설계다. 압축·전수 복원·그림 생성·모델 실행·T 열람·선택 잠금·Git 변경을 하지 않았다. 새 파일은 이 진단 폴더뿐이다. 이후 실제 결과가 생기면 고유한 새 후보를 만들며 현재 후보나 이 검토를 덮지 않는다.

## 확인된 크기

기존 후보는 197,872,712B이며 상한은 262,144,000B이다. 아직 빠진 [목록](../../gzip_extra_aux_20261016_v1/files/item_0600.csv.gz)은 42파일·2,492,213B다. whole453 감사 19파일, post-final v2 준비물 9파일, REPLAY44 검토 8파일, ROOT 메타데이터 검토 1파일, K8 recipe 5파일이다. 이 목록은 해당 시점의 SHA로 봉인했으며 실제 K8 bundle·추후 corecost·T·E0B·최종 replay/감사/보고서 완료를 뜻하지 않는다.

이 둘만 합치면 200,364,925B, 남은 공간은 61,779,075B다. 옛 report/figure pair의 19,004,267B는 참고 크기이며 고정 요구나 절감액이 아니다. 이미 후보에서 빠진 옛 pair를 다시 빼서 절약을 두 번 계산하지 않는다. 새 최종 pair는 실제 크기를 추가해야 한다.

기존 후보의 이미지 38개는 7,161,606B다. 봉인된 파일 SHA 목록에서 PNG/SVG 바이트 중복은 0개였다. 이 이미지를 중복이라고 간주해 절약액을 잡지 않았다. 기존 진단 그림을 제외하려면 실제 새 최종 산출물과의 역할·연결을 먼저 확인해야 한다.

## T40 추정과 미확인 비용

최신 E2 pack 실측 비율을 적용한 T40 archive+metadata 추정은 49,304,257B다. 보수적 시나리오의 79,667,149B는 archive만의 수치이며 같은 metadata 예약 3,145,728B를 더하면 82,812,877B다. 두 수치 모두 미래 오차 통계의 실제 크기나 수학적 상한이 아니다. 동일 자료의 V 압축 비율이 T에도 유지된다는 보장이 없다.

[BUDGET.json](../../gzip_extra_aux_20261016_v1/files/item_0599.json.gz)은 final pair를 8MiB·12MiB·옛 pair 크기로 각각 가정한다. K8은 5,000,000B 목표값, 나머지 corecost/E0B/replay/감사는 3MiB 예시값으로 계산했다. 이 두 예시값은 관측치나 상한이 아니며 각 실제 산출물 크기로 교체해야 한다. 전체 숫자 CSV와 필수 여섯 그림 그룹은 유지한다. 8–12MB 수준의 curated pair가 가능한지는 실제 생성 후 확인한다.

예를 들어 8MiB pair, T40 49,304,257B, K8 5MB, 기타 3MiB를 가정하면 압축 추가 전 상한을 4,059,518B 넘는다. 아래 보조 원본 20,071,038B가 절반 크기로 저장된다는 **가정**을 적용하면 새 recipe/Markdown 파생물 오버헤드 전 5,976,001B 여유다. 12MiB pair에서는 같은 가정의 여유가 1,781,697B로 줄어든다. 실제 gzip이나 T40 크기가 아직 없으므로 공간 충족을 약속하지 않는다. 보수적 T40 시나리오는 훨씬 더 많은 공간을 요구한다.

## 실제 압축 후보

[AUX_GZIP_CANDIDATES.csv](../../gzip_extra_aux_20261016_v1/files/item_0598.csv.gz)는 실제 gzip을 실행하지 않은 95파일·20,071,038B의 구체 목록이다. 기존 후보 또는 이번 안전한 새 metadata 목록의 SHA를 사용했다. 큰 과거 감사 결과, 입력 SHA 캡처, 진단용 JSON, 시간블록·채널패턴의 전체 CSV 등이 대상이다. 숫자·행·정밀도를 줄이지 않고 원본 바이트의 gzip과 원 SHA를 게시하며 별도 임시 경로의 전수 복원으로 증명할 수 있다.

탐색에 필요한 canonical registry, SELECTION_LOCK, 최종 SCORES/COST, 데이터 계약, 모델 자산, 실제 fit/prediction manifest·reference·selected binding은 이 목록에서 제외했다. 파일명에 MANIFEST·REFERENCE·BINDING·PLAN·QUEUE가 있는 파일도 보수적으로 제외했다. 원 source·고정 plan·checkpoint·reference 내용은 변경하지 않는다.

우선 원본 크기 내림차순으로 큰 파일을 검토하되, 실제 실행 시에는 아래 순서를 따른다.

1. ROOT가 정밀 비용 측정 종료를 확인한 후 원본 SHA를 다시 봉인한다. 변경된 파일은 이전 SHA로 압축하지 않는다.
2. 기존 `publication_derivatives/gzip_1792092403733272600_v3`를 변경하지 않고 고유한 새 aux 폴더를 만든다. 각 원본과 gzip의 크기·SHA, 원 상대경로·복원 명령을 기록한다.
3. gzip을 별도 임시 경로에 전수 복원하여 원본 바이트와 SHA를 확인한다. 원본 전체를 로컬에 보존한다. clone 실행 API가 원 경로를 요구하면 먼저 정확 복원을 실행하도록 설명한다.
4. 직접·전이 Markdown 링크를 찾는다. 영향을 받는 원 Markdown을 보존하고 새 렌더용 Markdown만 만든다. Markdown→Markdown은 렌더용 새 `.md`를 우선 연결하며, 데이터 링크만 `.gz`를 가리키게 한다. 기존 v3 파생 Markdown도 영향을 받으면 새 파생물로 연결하고 원본은 보존한다.
5. 실제 압축 결과·복원 증거·새 렌더 링크를 모두 확인한 뒤에만 새 후보에서 해당 원문을 gzip 표현으로 바꾼다. 새 recipe·manifest·복원 증거·전이 Markdown의 크기까지 순증분에 합산한다.

## 실제 최종 생성 후 후보 갱신

GPU 작업, replay, 허용된 T·E0B 평가가 실제 영수증으로 종료된 뒤 입력 범위를 봉인한다. rootcanonical registry/최종 SCORES·COST와 lock은 ROOT가 실제 상태에 맞게 확정한다. 미완료 학습·원래 재개 큐는 그대로 남기며 비용이나 음성 수치 때문에 제거하지 않는다.

CPU 후처리는 기존 A-only pattern snapshot을 그대로 재사용한다. 최신 V와 허용된 T에 group errors·물리 단위 지표·시간블록 차이를 계산하고 재적합하지 않는다. 이후 기존 API로 고유한 새 출력 폴더를 만든다.

```python
report_figures.generate(public_root, private_root, split='V_select')
# SELECTION_LOCK.locked==true 및 실제 감사 가능한 T manifest가 있을 때만:
report_figures.generate(public_root, private_root, split='T_final')
report_campaign.generate(public_root, private_root)
```

그림의 필수 그룹은 `accuracy_by_k`, `matched_controls`, `learning_diagnostics`, `cost_accuracy`, `lag_prefix_multik`, `representative_traces`다. 실제 evidence가 없는 그룹은 PENDING으로 남긴다. 예산·LR·seed·cohort가 다른 조건을 한 곡선이나 공정 비교로 합치지 않는다. PeMS의 시간축은 실제 달력 대신 elapsed time을 유지한다. 전체 원수치는 CSV로 보존하며 대표 trace의 원자료 배열은 공개하지 않는다. V/T snapshot을 각각 명시적으로 연결하고 실제 생성 후 PNG/SVG를 확인한다.

마지막 새 FILE_LIST는 기존 4,600 목록에서 출발한다. 이미 승인된 원문 보존·공개 제외는 유지하고, exact lossless 표현으로 바꾼 파일과 새 최종 산출물만 증감한다. 원본 파일 삭제나 기존 후보 덮어쓰기를 하지 않는다. 모든 새 파일의 실제 크기, 20MiB 개별 상한, 250MiB 전체 상한, privacy/case/relative-link/schema/image 검사와 필요한 전수 복원 증거를 확인한다. 증거를 연결한 canonical README와 실제 최종 report가 있어야 게시 후보를 확정한다. 여기서는 stage/commit/push를 수행하지 않는다.
