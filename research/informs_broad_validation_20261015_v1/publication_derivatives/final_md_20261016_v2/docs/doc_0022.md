## 4. ROOT가 나중에 사용할 작은 launcher API

아래는 ROOT의 **기존 active audit owner `lease` 안에서** 쓰는 코드다. 독립 CLI나 실행 중 training owner의 child 안에서 새 `GPUReservation`을 중첩하지 않는다. ROOT GPU 작업이 끝나지 않은 현재는 실행하지 않는다. `$A/$C`의 실제 루트는 기존 승인 환경변수를 사용한다.

```python
from pathlib import Path
import importlib.util
import os

p = Path(os.environ["INFORMS_PUBLIC_ROOT"])
path = p / "diagnostics/e0_b_execution_ready_20261016T012806/e0_b_launcher.py"
spec = importlib.util.spec_from_file_location("pinned_e0_b_ready", path)
module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(module)
result = module.run_with_owner(
    lease,
    os.environ["INFORMS_ASSET_ROOT"],
    os.environ["INFORMS_CACHE_ROOT"],
    max_seconds=float(os.environ["INFORMS_E0_B_MAX_SECONDS"]),
    gpu_devices=os.environ.get("CUDA_VISIBLE_DEVICES", "0"),
)
assert result["status"] == "E0_B_EXACT55_COMPLETE"
```

`max_seconds`는 ROOT가 실제 잔여 시간에서 정하는 child 상한이며 예상 시간이나 추가 자원 승인이 아니다. 기존 audit owner의 누적 GPU ceiling은 43200초 이하, hard wall은 `1792050350+172800` 이하이어야 한다. training lease는 거부한다. ROOT가 새 audit owner를 열 필요가 있으면 기존 owner와 모든 child 종료를 확인한 뒤 기존 `GPUReservation` API로 열고 이 함수에 넘긴다. launcher 자체에는 owner 생성 기능이 없다.

launcher는 C+R 합산 30GiB와 pending 1GiB 여유·각 디스크 여유를 확인한다. checkpoint bytes와 source/receipt pin을 다시 확인한 뒤 새 private `final_execution/e0_B_pinned_<stamp>/`에 log/result를 저장한다. fresh child는 thread2, offline, `lease.child_environment()`를 받고 정확한 9-ID inventory를 다시 검증한다. 55개가 하나라도 추가·누락·변경되면 실제 B 호출 전 거부한다. 수동 in-memory API 교체나 모델 변경은 없다.

부모는 child가 끝날 때까지 기다려 owner를 먼저 닫지 않는다. deadline은 batch/actual foundation forward 경계에서 검사한다. 이미 제출된 CUDA 연산을 강제로 취소하는 타이머는 없다. 외부 프로세스·기존 ROOT 작업을 종료하지 않는다.

## 5. 완료 판단과 새 출력

실제 API는 `legacy_e0/evaluation/<id>/cp<update>/`에 reference seal, prediction manifest, public sufficient statistics, independent rescore를 만들고 private cache에는 predictions archive를 둔다. 기존 immutable archive가 있으면 원 API의 reference/hash/score 검증 뒤 재사용하며 `executed_now=false`로 구분한다. 새 output은 공개 `execution_batches/E0_B_PINNED_<stamp>.json`과 private child log/result에 연결된다. source30·main registry 변경 여부, 실제 F calls/streams, raw child exit code와 평가 status를 함께 남긴다.

완료는 child exit0만으로 판단하지 않는다. 정확한 inventory55, `EVALUATION_COMPLETE`, rescored55, recorded B MSE/MAE curve match55(absolute tolerance 1e-7), source30·registry byte 불변을 모두 요구한다. partial/budget/route/model/reference/curve mismatch는 원 API 산출물과 private log에 보존하고 `E0_B_INCOMPLETE_REVIEW_PRIVATE_LOG`로 남긴다. 전체 연구 완료를 선언하지 않는다. 새 main SCORES, registry, selection lock은 launcher가 만들지 않는다.

실행 후 ROOT의 기존 CPU `audit_campaign.audit_all`로 저장 legacy B archives를 독립 재채점하고 `LEGACY_B_AUDITS.json` 범위를 확인한다. 이 후속 감사도 이번 준비에서는 실행하지 않았다.

## 6. 시간·비용 근거

[확인] 최신 준비 근거인 실제 inventory는 API 3.266초, 전체 driver 4.922초, peak RSS 528,809,984 bytes, safe torch.load 73회였다. 이는 checkpoint 검증 시간이며 B 재추론 시간으로 바꾸어 쓰지 않는다. checkpoint55 파일의 stat 합계는 11,020,767 bytes이고 이번 준비는 그 weight byte를 읽거나 역직렬화하지 않았다.

[확인] capture 시 `legacy_e0/evaluation` 실제 B manifest/registry receipt는 없었고, 기존 공개 diagnostics와 legacy output에서도 `saved_weight_full_legacy_B_reinference_not_training` 실측 결과를 찾지 못했다. 따라서 **55 checkpoint 실제 B 총 GPU wall은 불명확**하다. 다른 PeMS 배포 비용의 1210초나 학습 step 시간을 B55 시간으로 환산하지 않는다.

실행하면 각 checkpoint manifest의 `cost.replay_wall_seconds`, `actual_F_calls`, `actual_F_streams`, origin 수와 batch8/row128을 실제 측정한다. ROOT owner charge는 준비·모델 로드·safe-load·child 대기·close까지 포함하므로 checkpoint replay 시간의 합보다 클 수 있다. 최초 checkpoint 실측으로 잔여 시간을 갱신하되 resource 상한을 늘리거나 route를 임의 대체하지 않는다. 수치 불일치는 실패 원인으로 남기며 좋은 결과를 만들기 위해 기존 curve나 source를 수정하지 않는다.
