## 무엇을 바꿨는가

[원 launcher 공개 안전 사본](../../../diagnostics/multik_postfinal_resource_1792096163404501000/original_multik_launcher.py)은 실제 private 원본 fe629d2586…와 byte가 같다. [정적 파생본](../../../diagnostics/multik_postfinal_resource_1792096163404501000/postfinal_multik_launcher.py)은 **`_owner` 한 함수만** [명시적 새 자원 gate](../../../diagnostics/multik_postfinal_resource_1792096163404501000/postfinal_gate.py)를 호출하도록 바꿨다. 그 함수 밖의 prefix/suffix bytes와 다른 모든 최상위 AST 노드가 원본과 같다. run/resume·worker 명령·원20 queue·입력 pin·warmup10/timed20·검사·수치 관용오차는 그대로다. runtime monkeypatch, lease 위장, 원 pin 변경은 하지 않았다.

원 pre-final 비용 누적 ceiling은 **39,600초**다. post-final은 최종 reserve를0으로 명시하여 **전체 누적43,200초 중 남은 시간만** 사용한다. 새43,200초를 주거나 원 campaign48h/합산30GiB를 늘리지 않는다. 근거는 [비용 계약75–79](../../../COST_PROTOCOL_KO.md)와 원 `cost_campaign.py --reserve-final-seconds 0` 규약이다. 총예산이 이미 소진됐으면 새 owner를 시작하지 않는다. 비용 실패나 비선점 teardown 초과는 원 영수증과 queue에 남고 성공으로 바뀌지 않는다.

## 실제 실행 gate

- 잠금된46개와 공식 T batch의 exact46 PASS/중복 없음/실패0/deferred0/동일 selection SHA를 확인한다. 각 실제 T manifest의 route/data/scaler/artifact/source metadata가 lock과 맞아야 한다. 이는 새 수치 재검산 자체를 대신하지 않는다.
- 고정9 legacy ID의55개 `(id,update)`와 file/state/path/scope/원곡선 fingerprint가 실제 E0 inventory와 같아야 한다. 완료 manifest/reference/독립 FP64 rescore를 연결한다. 곡선 MATCH는 필수 성공조건이 아니다.
- `CURVE_SCORE_MISMATCH`는 실제 추론·rescore 종료로 인정한다. `REPLAY_FAILED`는 actual_F_calls>0인 실제 추론 시도 실패만 인정하고 실패 개수로 남긴다. 로드 실패(F0), BUDGET_PENDING, id-only route failure, 누락·중복은 거부한다. 55개를 단순 열거한 것을 실제55개 추론 완료라고 쓰지 않는다.
- `phase_owners` 두 항목은 T batch/E0 registry의 exact binding, 실제 owner safe-fields, 중앙 closure의 동일 lease ID와 실행 시간 구간을 연결한다. 같은 single owner면 두 항목이 같은 safe-fields/closure를 가리킨다. safe-fields에는 `lease_id,pid,create_time,started_unix,authorized_children`가 필요하다. ROOT final caller는 인증 child PID/create_time 목록을 끝에 별도 불변 safe snapshot으로 남겨야 한다.
- 그 owner·모든 authorized child의 PID/create_time 집합이 `prior_processes`와 같고 실제로 종료됐어야 한다. ACTIVE 부재를 확인하고 중앙 OS lock으로 단일 owner를 취득한다. 다른 작업은 종료하지 않는다.
- 현재 T 시간 gate는 최초 T reference 생성부터 완료 batch까지 한 owner가 포괄하는 설계다. 여러 owner에 걸친 부분 T 재개는 이 gate가 거부할 수 있다. 실제 그 상황이 생기면 원 결과를 보존하고 해당 증거 연결을 별도 검토해야 하며 자동으로 통과시키지 않는다.
- 원 source39·원 helper/pins·선택 검토46은 불변이어야 한다. 저장/여유·48h·전체 GPU ledger를 확인한다. 원20 queue 순서는 유지한다. 최신 partial batch를 명시 경로와 SHA로 받고 원 `_resume`가 기존 **완료 scope**의 모든 파일SHA와180 trial 구조를 다시 검증한 뒤에만 재사용한다. partial scope의166 trial 등을 완결180으로 합치지 않고 원 결과를 보존한 채 fresh scope를 실행한다.

## ROOT 호출

[caller 공개 사본](../../../diagnostics/multik_postfinal_resource_1792096163404501000/root_postfinal_caller.py)은 private ROOT caller와 byte가 같고 사용자 절대경로를 포함하지 않는다. 세 root 환경변수는 기존 캠페인 위치를 가리켜야 한다. **원 launcher 자체의 default CLI는 자산해시도 읽으므로 이번 metadata 준비에는 아래 caller만 사용한다.**

```powershell
& "$env:INFORMS_ASSET_ROOT/.venv/Scripts/python.exe" -X utf8 -B "$env:INFORMS_PUBLIC_ROOT/diagnostics/multik_postfinal_resource_1792096163404501000/root_postfinal_caller.py"
```

아래는 ROOT가 실제 final proof와 최신 partial receipt를 봉인하고 별도 신호를 준 뒤의 형식이다. 준비 과정에서는 실행하지 않았다.

```powershell
& "$env:INFORMS_ASSET_ROOT/.venv/Scripts/python.exe" -X utf8 -u -B "$env:INFORMS_PUBLIC_ROOT/diagnostics/multik_postfinal_resource_1792096163404501000/root_postfinal_caller.py" --execute --root-triggered --final-proof-json "$env:INFORMS_PUBLIC_ROOT/<actual-final-proof.json>" --final-proof-sha256 <actual-sha256> --resume-receipt-json "$env:INFORMS_PUBLIC_ROOT/<latest-partial-BATCH_LAUNCHER_RECEIPT.json>" --resume-receipt-sha256 <actual-sha256>
```

`INFORMS_POSTFINAL_PROOF_JSON/SHA256`는 이 명시 인자를 현재 process와 child 환경에 전달하는 경로일 뿐 자동 승인이나 숨은 상한 변경이 아니다. 값/인증 token을 공개 영수증에 출력하지 않으며 종료 시 제거한다. 실제 proof는 공개 상대경로·SHA만 담아야 한다. 개인 경로나 비밀값을 넣지 않는다.

## 실제 확인한 범위

합성 metadata9개와 기본 metadata CLI(exit0), proof 없는 `--execute` 거부(exit2)를 실제 확인했다. 새 gate가 없던 RED7실패와 owner cross-binding이 없던 RED2실패를 확인한 뒤 GREEN9를 얻었다. 학습/추론/배열·checkpoint hash·대규모 source 실행·GPU/T/전체 rootpytest는0이다. 기존 CPU421개 suite에 새9개가 포함됐다고 말하지 않는다. 실제 final proof·GPU 자원phase·원 scope 재검증은 앞으로 ROOT가 실행해야 하는 범위다.
