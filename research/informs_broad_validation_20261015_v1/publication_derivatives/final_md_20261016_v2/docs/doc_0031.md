ROOT가 V/비용 원리에 따른 방법과 strong baseline의 명시 후보를 아직 확정하지 않았다. 그 결정 전에는 lock 가능한 최종 목록이 준비됐다고 판단하지 않는다. 원 runbook·source·결과는 보존했다.

현재 결론: runbook의 상태 assertions는 대부분 적절하며 예외를 성공으로 바꾸지는 않는다. 아래 운영 gate를 지키고, 최신 flat 점수 반영 순서를 보완해야 COMPLETE/PASS를 전체 연구·자원 계약 완료로 오인하지 않는다. 코드 수정이나 새 실험은 이 감사에서 요청하지 않는다.

## 물질적인 범위·실행 gate

**F01 — 실행 전 source pin**

[확인] 원 INPUT_SOURCES.sha256의 27행은 빈 줄이고 원 PowerShell loop는 이를 걸러내지 않아 빈 경로를 hash한다. 승인된 report_campaign.py/report_figures.py 변경 2개도 옛 pin과 다르다. 이대로는 source 검증이 정상 통과할 수 없다. 옛 파일을 보존하고 빈 줄을 제외한 최신 freeze를 확인한다. JSON에 현재 26 pins와 18 lock sources를 기록했으며 scientific six는 기준 SHA와 모두 같다.

**F02 — replay PASS는 lock 외부 gate**

[확인] lock_selection/_validated_lock은 replay receipt를 읽거나 SHA로 잠그지 않는다. runbook의 replay 전체 PASS 및 selected⊆replayed 검사가 실제 필수다. 재사용 replay는 reference/source/route/standard V/archive 결박을 검사하지만 requested tolerance와 batch_size는 reference에 없다. 기존 receipt의 실제 atol1e-5/rtol1e-4와 PASS·정확한 ID·선택 V를 확인한다. 실패 receipt를 바꾸거나 tolerance를 낮추지 않는다. 근거: final_evaluation.py:191–253; route_predictions.py:221–255.

**F03 — global SCORES 순서**

[확인] 현재 public-root SCORES.csv는 없다. T는 route별 local SCORES만 쓰며, audit_all은 root flat 파일이 존재할 때에만 manifest마다 global run/split/cohort 정확히 1행을 강제한다. ROOT가 확인한 순서인 ‘모든 V/T/E0 writer와 owner 종료 → 최신 report flat SCORES 생성 → root에 한 번 반영 → final audit_all’을 따른다. 최종 감사에서 global_scores_checked=True도 확인한다. absent 상태 PASS는 global flat 검산 완료가 아니다. 근거: route_predictions.py:171–185; audit_campaign.py:344–385; report_campaign.py:970.

**F04 — available 감사와 계획된 범위**

[확인] audit_all은 존재하는 manifest를 감사하며 선택 전원 T/비용/replay/E0 계획 목록의 누락을 완전히 강제하지 않는다. mandatory completeness도 registry status 기준이다. T batch의 run_ids/PASS record 집합이 lock.allowed_run_ids와 정확히 같고 selection_sha256이 같아야 하며, 최종 독립 T audit도 같은 집합을 포함해야 한다. COMPLETE_SELECTED_ROUTES는 그 explicit batch 완료이고 campaign 완료가 아니다. route_predictions-only V는 현재 _standard replay 입력이 아니므로 잠금 전에 후보별 입력 위치를 확인한다. 근거: audit_campaign.py:321–343, 397–412; final_evaluation.py:338–347; route_predictions.py:190–200.

**F05 — COMPLETE와 deadline 준수는 별도**

[확인] 신규 route는 각 origin batch 앞에서 deadline을 검사하지만 F row chunk 내부 및 마지막 inference/save 뒤 검사는 없다. E0는 각 실제 F model 호출 pre-hook이 있으나 마지막 scoring/save 뒤 COMPLETE 전 deadline 검사는 없다. 마지막 batch·압축·close 중 기한 초과해도 결과는 COMPLETE일 수 있다. 최종 owner charge의 deadline_overrun_seconds·누적 process-wall·campaign wall을 별도로 확인하고 저장/종료 여유를 둔다. 실제 초과 발생을 주장하는 것은 아니다. 근거: route_predictions.py:78–116, 168–185, 237–255; gpu_runtime.py:28–49; legacy_evaluation.py:191–218, 450–465; resources.py:264–280.

**F06 — storage gate와 부분 파일**

[확인] resources.check_storage_budget(30 GiB)는 존재하지만 이 final/replay/E0 경로에 호출 연결이 없다. archive를 xb로 먼저 쓴 뒤 manifest/statistics를 순차 저장하여 I/O 실패 시 부분 immutable 산출물이 남을 수 있다. 이후 존재하는 archive를 재사용하려다 완성 manifest가 없어 거부될 수 있다. ROOT 권한 범위에서 actual free space·cache cap·보수적 pending bytes를 먼저 확인하고, 실패 시 최초 오류와 부분 파일을 보존한다. 존재만으로 완료/무작정 재시도·덮어쓰기로 판단하지 않는다. 근거: resources.py:348–360; route_predictions.py:151–185, 229–255; legacy_evaluation.py:171–218.

**F07 — OOM 및 비용 row와 평가 row**

[확인] final wrapper의 origin batch는 default4이고 RAW F rows는 default full이며 cost에서 고른 가장 빠른 성공 row를 자동 상속하지 않는다. OOM은 generic failure로 보존되고 자동 row 축소/fresh child 재시도는 없다. legacy model/state 해제는 success 경로에만 있다. 비용의 row별 성공을 final full-row 적합성으로 확장하지 않는다. 실패/보류를 모두 확인하고 최초 OOM 근거를 보존한다. exit0 또는 owner CLOSED만으로 완료라고 하지 않는다. 근거: final_evaluation.py:306–345; deployment.py:278–286; legacy_evaluation.py:433–445.

**F08 — E0 COMPLETE와 재사용 라벨**

[확인] E0 inventory의 NO_NEW_B_CHECKPOINTS는 summary failed 목록에 없으므로 다른 route가 있으면 COMPLETE일 수 있다. 원 runbook의 all READY/nonempty·checkpoint READY·rescored==available 검사가 이를 막는다. NO_RECORDED_B_SCORE도 허용되므로 모든 CP의 기록 curve 일치와 동일하지 않다. 기존 cache identity에는 inference batch/row가 없어 다른 물리 row의 artifact를 재사용할 수 있지만 summary budget.row_microbatch는 현재 요청값이다. 실제 fresh/reused·MATCH/no-record counts와 reused manifest.cost의 row/batch를 나누어 보고한다. ID/update 결과와 최종 LEGACY_B_AUDITS coverage를 대조한다. E0 B는 과거 development 자료다. 근거: legacy_evaluation.py:91–98, 181–186, 295–318, 414–465; audit_campaign.py:294–305.

## ROOT의 최소 확인 순서

1. 후보·strong baseline·legacy 범위를 V/비용으로 명시 고정한다. 이 감사는 방법을 고르지 않았다.
2. 승인된 편집 종료 후 최신 pin/six/source18을 확인한다. 기존 GPU owner와 child 모두 종료, registry RUNNING의 실제 처리 근거, 저장 여유와 종료 여유를 확인한다. _quiescent만으로 전체 child 종료가 증명되지는 않는다.
3. 외부 audit owner에서 replay를 수행하고 exact ID/PASS/tolerance/current binding 및 fresh/reused를 확인한다. COMPLETE/failed0/deferred[]를 모두 검사한다.
4. owner 종료 후 선택 V 독립 감사와 exact record를 확인하고 명시 경로로 immutable lock한다. selected⊆PASS replay와 mandatory partial 범위를 보존한다.
5. execute_T의 full gate를 사용하여 lock ID/selection SHA/exact PASS 집합을 확인한다. reused artifact의 cost_record F streams를 새 forward 지출로 합산하지 않는다.
6. fresh authenticated child에서 E0를 수행하고 원 runbook의 ID/inventory/count gate와 CP update/curve/재사용 범위를 대조한다. owner/child 종료 후 charge·overrun을 확인한다.
7. 모든 writer 종료 후 최신 flat 점수를 root에 한 번 반영하고 final audit_all의 errors0/PASS/global_scores_checked와 exact T/E0 coverage를 확인한다. 마지막 보고서는 이 실제 audit 경로와 partial 범위를 인용한다.

[확인] 자료/모델/live lease/free space를 읽지 않았으므로 현재 GPU 인계·용량·실제 완료 여부는 이 문서에서 확인하지 않았다. 읽기 중 입력 source/runbook SHA는 변하지 않았고 frozen six 6/6이 유지됐다. 테스트·평가 실행으로 검증한 문서가 아니며 단일 검토자 source audit이다. 기존 child에게 독립 검토 재개를 요청했으나 agent thread limit으로 사용할 수 없었다.
