# 선택된 encoder의 의존성·좌표·연산량 진단

## 실제 실행과 결론 범위

[실행 영수증](../../gzip_extra_aux_20261016_v1/files/item_0346.json.gz): 18 완료/6 제외/0 실패, 실제 진단 1.70초, process exit0. Torch import 전에 CUDA_VISIBLE_DEVICES를 빈 문자열로 고정했고 CUDA context 미초기화, CPU threads2, 실제 F 호출0, 학습 update0이었다. Receipt·artifact SHA와 원 data/scaler hash를 확인하고 선택된 weights를 CPU 모델에 exact하게 로드했다. Registry/SCORES/기존 artifact는 수정하지 않았다.

이 결과는 encoder의 입력 의존성과 단계·연산량 검사다. 예측 성능 개선, 독립 일반화, 충분 학습 또는 데이터 준비 전 과정의 누출 부재를 증명하지 않는다.

## 과거 창 안의 뒤쪽 정보를 사용하는가

각 모델의 첫 V origin에 대해 정확히 L512의 정규화된 과거 창만 뽑았다. t=256 뒤의 행257..511에 결정적 perturbation을 더하고 z의 행0..256이 바뀌는지 검사했다. 이 뒤쪽 행도 origin 이전 과거다. 바뀐다는 것은 완성된 과거 창 안에서 뒤쪽 과거에 의존한다는 뜻이며 미래 target 사용과 구분해야 한다.

Beijing의 최대 변화는 다음과 같다.

```text
family          K3          K6          K11
B0              0           0           0
causal7         0           0           0
bidirectional7  0.409610    0.422677    0.384688
B2              0.722132    0           0.510840
```

B2 K6는 선택된 search CP가 0이며 초기 front residual 출력이0이다. 따라서 이 weight의 변화0을 B2 구조 전체가 prefix-causal이라는 증거로 쓸 수 없다. 같은 이유로 bidirectional lag weights가0인 초기 모델도 한 번의 변화0만으로 일반적인 causality를 증명할 수 없다. 이번 선택된 Beijing bidirectional 모델의 lag weight 최대 절댓값은 약0.0845–0.0941로 실제 학습 후0이 아니었다.

PeMS B0는 세 K 모두0, B2 K43/85/170은 각각1.147014/1.330937/0.259598이었다. 이 수치의 크기는 정규화 입력과 특정 선택 weights·perturbation에 종속된 진단량이다. 예측 오류 크기나 성능 순위가 아니다.

## 합성 이동 창의 내부 정렬

실제 시계열에서 L+H를 더 읽지 않았다. Seed20261015로 만든 **합성** 길이 L+H 벡터에서 완전한 L 창 두 개를 H만큼 이동시켰다. 겹치는 구간에서 왼쪽32와 오른쪽16을 제외했다. 이는 causal padding과 bidirectional 오른쪽 경계의 차이를 제외하기 위한 고정 좌표다.

Beijing B0/causal7/bidirectional7의 내부 겹침 표현 차이는 모두0이었다. B2 K3/K11은0.497182/0.429293, CP0 K6는0이었다. PeMS B0는0이고 B2 K43/85/170은1.286831/1.282180/0.479191이었다. 전체 과거 창을 섞는 front는 창 경계와 row 좌표가 바뀌면 같은 합성 관측의 표현도 달라질 수 있다. 이 검사는 실제 긴 context의 성능 benchmark나 실제 미래 정보 이용 실험이 아니다.

## D prefix와 parameter/forward FLOPs

18개 모두 `D[lag,:K,:]`의 명시적 lag별 합과 실제 decode가 allclose였다. 최대 절대 오차는2.384×10⁻⁷이며 tolerance는 atol1e-5/rtol1e-4였다. Dummy future는 마지막 과거 latent를 반복한 값이고 실제 F 추론이 아니다.

Parameter와 torch.profiler CPU 지원 연산의 forward FLOP 추정치를 P/E와 D로 나눠 저장했다. 실제 encoder를 실행했고 D는 같은 dummy future로 실행했다. B1, L512이며 Beijing H48, PeMS H12다. 예를 들어 Beijing K3은 다음과 같다.

```text
family          parameters    P/E supported FLOPs    D supported FLOPs
B0                    264                 33,792               22,187
B2                 34,323              1,486,848               22,187
causal7               462                245,760               22,187
bidirectional7        462                245,760               22,187
```

정확한 행렬곱 산식 참고치는 E=2BLCK(시차 encoder는×7), D=2BH·7KC다. Beijing K3의 E 행렬곱은 pointwise33,792/시차236,544, D는22,176이다. P의 mixing 연산은 이 E 참고 산식에 포함하지 않는다. [전체 원수치 CSV](../../gzip_extra_aux_20261016_v1/files/item_0347.csv.gz)와 각 run JSON에는 operator별 profiler 추정치·zero/unaccounted 목록·parameter 수가 있다.

Profiler가0으로 기록한 nonlinear/reduction/memory 연산을 FLOPs가 없다고 해석하면 안 된다. Broadcast 산술도 profiler 구현의 추정 방식에 좌우되므로 지원 연산 합이 모든 산술의 정확한 총량을 뜻하지 않는다. Backward, F, 실제 end-to-end 시간/메모리와 데이터 전송 비용은 포함하지 않는다. 별도 배포 비용 측정으로 판단해야 한다.

## 자료·누출 해석의 한계

각 JSON의 future-target 미사용 표시는 target_window를 뽑아 encoder/probe에 넣지 않았다는 계산 범위를 뜻한다. Task loader가 허용 safe FIT archive를 로드·검증하는 과정에서 파일 전체를 역직렬화하지 않았다는 byte-level I/O 주장이 아니다. 기존 data contract의 archive/normalization ancestry 한계는 이 진단이 해결하지 않는다. 추가 실제 H 구간을 합성 정렬 실험의 입력으로 사용하지 않았다.

합성 CPU unit suite는 최초4 RED 후4 GREEN이었다. 실제18개 selected-model 진단도 위에 구분해 완료했다. 실제 forecast gain과 모델 선택은 원 학습/추론·최종 잠금·독립 채점 결과로 판단해야 한다.
