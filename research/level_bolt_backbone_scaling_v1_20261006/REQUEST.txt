# CLI 실행 지시문 — Chronos-Bolt backbone scaling vs LEVEL
# 목적: "큰 Bolt-small을 C→K로 압축 + LEVEL 보정"과 "더 작은 동일 Chronos-Bolt 계열을 원채널 C개 그대로 사용" 중
# 어느 자원 배분이 더 타당한지, 동일 데이터·평가·비용 계약에서 직접 비교한다.

[최상위 목적]
현재 fixed-PCA LEVEL의 실용적 핵심 주장인
"큰 단변량 TSFM이 처리하는 계열 수를 줄이고, 압축에서 제외된 성분은 작은 외부 G로 보완하는 방식"
이
"더 작은 동일 Chronos-Bolt backbone을 선택하고 모든 원채널을 그대로 예측하는 단순 대안"
보다 정확도–추론비용 관점에서 선택할 이유가 남는지 판정한다.

이번 실험은 새 LEVEL 변형을 개발하는 회차가 아니다.
Bolt-mini/tiny에 LEVEL을 자동으로 붙이거나 LoRA를 학습하거나 새 G를 설계하지 않는다.
첫 질문은 오직 다음이다.

    larger backbone + fewer latent series + LEVEL
    versus
    smaller backbone + all original series

[판정 소비처]
INFORMS/논문에서 다음 질문에 답하기 위한 근거다.

1. "왜 Bolt-small을 압축하지? 그냥 더 작은 Bolt를 원채널에 쓰면 되지 않나?"
2. "채널 수를 줄이는 전략이 backbone 자체를 줄이는 전략보다 실제로 유리한가?"
3. LEVEL의 효율성 이득이 단순히 큰 backbone을 유지한 결과 때문에 사라지는가?

이 비교는 Chronos-2/Chronos-2-Small과의 system-level 비교와 구분한다.
이번 primary 비교는 가능한 한 같은 Chronos-Bolt family 안에서 backbone size와 channel allocation만 바꾸는 practical allocation comparison이다.

   - PCA 없음, G 없음, LoRA 없음.

- horizon H = 48 observations
- 기존 TRAIN/VAL/TEST-A/TEST-B 경계
- 기존 origin 목록 그대로
- TRAIN 통계로만 표준화
- 기존 입력 결측 대체 그대로
- 실제 target mask 그대로

- TEST 중 업데이트/online fitting 없음

Mini/Tiny에만 유리하거나 불리한 별도 정규화/긴 context/다른 horizon을 주지 않는다.

────────────────────────────────────────
4. Bolt F0 wrapper 계약
────────────────────────────────────────

Mini/Tiny는 기존 Bolt-small F0와 동일한 의미의 wrapper로 구현한다.

입력:
    x: [B, 512, C]

채널독립 Bolt 호출 직전:
    [B, 512, C]
      -> transpose
    [B, C, 512]
      -> reshape
    [B*C, 512]

각 원채널은 독립 단변량 task다.

출력:
- native quantile output에서 정확히 q=0.5 사용.
- 첫 48 observation.
- [B*C,48] -> [B,48,C]로 원래 순서 복원.
- 최종 FP32 CPU output.
- 원래 TRAIN-standardized coordinate 그대로 평가.

기존 Bolt-small wrapper를 재사용할 수 있으면 최대한 재사용하고
backbone model ID/revision만 일반화한다.
Mini/Tiny만을 위한 다른 후처리를 만들지 않는다.

────────────────────────────────────────
5. 사전 구현 검증 — TEST 전에 통과해야 함
────────────────────────────────────────

TEST 예측 전 VAL 또는 고정 TRAIN probe로 다음을 검증한다.

각 Mini/Tiny에 대해:

1. shape
   input [B,512,C] -> output [B,48,C]

2. finiteness
   input/output finite.

3. quantile
   실제 0.5 quantile index를 모델 config에서 찾아 사용.
   "mean"이라는 API 이름을 median으로 오해하지 않는다.

4. channel independence
   같은 origin에서 channel j의 과거를 바꿨을 때
   다른 channel i의 출력은 허용 오차 내에서 변하지 않아야 함.
   현재 F0 의미가 채널독립임을 실제 forward로 확인.

5. origin isolation
   batch 내 다른 origin을 바꿔도 해당 origin의 결과는 변하지 않아야 함.

6. batch/order parity
   단독 origin 실행 vs B4 실행의 대응 origin output.
   원점 순서를 permutation 후 복원한 output.
   기존 수치 허용오차 정책을 재사용하고 임의 확장 금지.

7. future barrier
   실제 미래 배열을 바꾸어도 constructed past input이 bit-identical이고
   prediction이 변하지 않아야 함.

8. frozen state
   eval mode, requires_grad False.
   pre/post model state hash 동일.

9. replay
   같은 input/같은 pinned checkpoint 재호출 시 기존 정책 내 일치.

10. Bolt-small anchor
   일반화한 wrapper로 기존 Bolt-small을 호출했을 때
   기존 F0 wrapper와 VAL prediction이 허용오차 내에서 일치해야 함.
   이 parity가 실패하면 Mini/Tiny TEST 전에 STOP_DEBUG.

사전검증 실패를 성능 음성으로 기록하지 않는다.

────────────────────────────────────────
6. 정확도 평가
────────────────────────────────────────

기존 BOLT_SMALL_LEVEL / BOLT_SMALL_F0:
- 동일 prediction artifact와 origin/mask가 검증되면 재추론하지 않는다.
- 저장 score를 그대로 믿기만 하지 말고,
  가능한 범위에서 기존 prediction manifest/hash/shape/origin binding을 확인한다.

Mini/Tiny:
- 설정 봉인 후 TEST-A/B를 한 번 평가.
- 새 hyperparameter selection 없음.
- zero-shot deterministic model은 seed 복제하지 않는다.

평가 집계는 기존 LEVEL/Chronos-2 campaign과 정확히 같게 한다.

Primary:
- channel-macro standardized MSE

Secondary:
- channel-macro MAE
- signed mean error/bias가 기존 pipeline에 있으면 함께 보존

반드시 보고:
- TEST-A
- TEST-B
- combined

combined는 A/B MSE 단순 평균 금지.
기존 방식처럼 채널별 SSE/count를 기간에 걸쳐 먼저 합산하고
채널 평균을 계산한다.

학습형 LEVEL 두 seed는 기존처럼 seed별 loss를 평균하며
prediction ensemble을 만들지 않는다.

자료 간 MSE를 평균한 하나의 총점 금지.

- 동일 resample 수
- method/origin/channel pairing 유지
- deterministic Mini/Tiny를 seed 두 개로 복제해서 표본 수를 늘리지 않음

새로운 임의 통계 방법이나 비열등성 margin을 만들지 않는다.
구간이 0을 포함하면 "차이 불확실"로 보고한다.
0 포함을 "동등"으로 해석하지 않는다.

이 비교는 이미 TEST가 노출된 후속 practical control이다.
독립 confirmation 또는 protected test라고 부르지 않는다.

8. 같은 회차 추론 비용 측정
────────────────────────────────────────

정확도 prediction 재사용 여부와 별개로,
비용은 이번 네 arm을 같은 새 measurement campaign 안에서 측정한다.

Primary cost arms:
- BOLT_SMALL_LEVEL
- BOLT_SMALL_F0
- BOLT_MINI_F0
- BOLT_TINY_F0

같은 장치/환경:
- 현재 RTX 4070
- FP32
- TF32 off
- 같은 torch/CUDA/chronos package environment
- CPU thread count 동일
- compile/quantization 금지
- model load 시간은 latency 밖
- disk/hash/score/log 시간은 latency 밖

입력:
- 각 dataset의 기존 VAL origins 중 첫 24개 chronological origins
- TEST를 비용 선택에 사용하지 않음

측정:
- B1 latency
- B4 throughput
- 10 warmups
- 10 full 24-origin passes
- 3 blocks
- block order rotate
- Bolt-small F0 pre/post sentinel로 drift 기록

timing scope:
standardized CPU input
-> reshape/transfer
-> actual online model inference
-> full original-channel H48 contiguous CPU output

LEVEL:
- C→K + Bolt-small + decode + G까지 전부 포함.
- "TSFM만" 따로 시간을 재서 LEVEL 비용이라고 하지 않는다.

Mini/Tiny:
- C original channels 전체 예측 완료까지 포함.

저장:
- ms/origin
- origins/s
- peak allocated
- peak reserved
- resident allocated after load/cleanup
- deployed parameter count
- parameter bytes
- buffer bytes
- total tensor bytes
- process CPU memory 가능하면 보존
- 모든 raw block 값

비용 비교는 중앙값만 남기고 raw block을 버리지 않는다.
block range는 confidence interval로 부르지 않는다.

[중요]
Mini/Tiny가 B4에서 OOM이면 OOM 자체를 결과로 기록한다.
B2 등 임의 batch로 primary 비교를 바꾸지 않는다.
B1은 계속 측정 가능하면 수행한다.

10. Phase 0 역주행 판정 규칙
────────────────────────────────────────

이 실험의 질문은 "Mini/Tiny가 더 좋은 모델인가?"가 아니다.
다음 설계 선택을 판단하는 것이다.

A = 큰 backbone의 처리 series 수를 줄이고 외부 보정
B = 작은 backbone에 모든 series를 그대로 처리

가능한 결과와 판정:

[Case 1]
Mini 또는 Tiny가 LEVEL보다
- MSE가 낮고(또는 통계적으로 유리한 방향)
- peak allocated도 낮고
- B4 throughput도 높음

판정:
CHANNEL_COMPRESSION_DEPLOYMENT_ADVANTAGE_REJECTED_FOR_TESTED_SETTING

의미:
현재 이 자료/하드웨어에서는
"큰 Bolt-small을 유지하며 채널을 압축"할 실용 선택 이유가 약하다.
LEVEL 내부 ablation 효과 자체를 부정하는 것은 아니다.

[Case 2]
LEVEL이 Mini/Tiny보다 정확하지만 비용은 더 큼

판정:
PARETO_TRADEOFF_REMAINS

반드시 정확도 차이와 비용 차이를 모두 보고.
"LEVEL superior"라고 단일 승리로 요약 금지.

[Case 3]
LEVEL이 정확도와 주요 비용 축 모두 유리

판정:
CHANNEL_COMPRESSION_ALLOCATION_SUPPORTED_IN_TESTED_SETTING

단:
세 자료가 노출된 후속 비교임을 유지.
범용 우위로 일반화 금지.

[Case 4]
Mini/Tiny 정확도 차이 구간이 0 포함 / 비용 축 방향 엇갈림

판정:
NO_SINGLE_DOMINANT_ALLOCATION

어떤 지표에서 어떤 방법을 선택하는지 조건부로 보고.

────────────────────────────────────────
11. 가장 강한 반론도 같이 평가
────────────────────────────────────────

각 결과에 다음 반론을 명시한다.

반론 A:
"Mini/Tiny는 smaller backbone이므로 더 싸지는 것이 당연하다."
→ 맞다. 이번 질문은 비용 감소 자체의 신규성이 아니라
  그 대가인 accuracy까지 포함해 어느 allocation이 더 유리한지다.

반론 B:
"LEVEL은 adaptation인데 Mini/Tiny는 backbone이라 method comparison이 아니다."
→ 맞다. 따라서 본 실험을 LEVEL method ablation으로 부르지 않는다.
  same-family practical allocation/system comparison으로 명명한다.

반론 C:
"Mini/Tiny가 이기면 LEVEL 설계가 틀렸다는 뜻인가?"
→ 아니다. 같은 Bolt-small 안에서 COMPRESS→LEVEL, LEVEL vs RAW 등의
  구조적 효과는 별도 증거다.
  여기서는 deployment 선택 이유만 판정한다.

반론 D:
"그럼 Mini/Tiny에도 LEVEL을 붙이면?"

12. 중단 기준
────────────────────────────────────────

즉시 STOP_DEBUG:
- 기존 Bolt-small wrapper parity 실패
- model revision/config binding 불명
- q=0.5 output 정의 불명
- origin/channel order 복원 실패
- 미래 배열이 입력 경로에 들어감
- data/mask/origin contract 불일치
- frozen state가 inference 중 변경됨
- baseline stored prediction/hash binding을 확인할 수 없음

STOP_RESOURCE:
- 기존 승인/사용자 허용 범위를 넘는 다운로드·GPU 시간 필요
- disk 예산 초과
- 기술 문제 해결을 위해 method/data contract 변경이 필요

성능이 나쁘다는 이유로:
- context 변경
- 다른 quantile
- rank/K 변경
- 다른 모델 revision
- 추가 tuning
을 열지 않는다.

14. 검산
────────────────────────────────────────

마지막에 최소 확인:

- Mini/Tiny model revision & hashes sealed
- actual parameter count recorded
- prediction origin order exact
- output shape/dtype/finiteness
- no future leakage
- channel independence verified
- existing LEVEL/F0 prediction binding verified
- scoring replay or stored-row consistency
- cost input hash identical across arms
- same timing scope
- all 3 blocks present
- no missing required arm
- failed/partial attempts preserved
- no unrelated files modified
- TEST 이후 설정 변경 없음

자체 검산 PASS를 독립 재현이나 논문 신규성 인증이라고 부르지 않는다.

────────────────────────────────────────
15. 실행/게시
────────────────────────────────────────

위 계약을 로컬 실제 파일에 맞춰 구체화한 뒤,
같은 범위의 구현·preflight·고정 평가·비용 측정·검산·보고까지 진행해.

기존 동일 결과가 발견되면 재실행하지 않고 재사용 근거를 남겨.
기술적인 path/API/serialization 오류는 method/data contract를 바꾸지 않는 범위에서 수정 가능하며
실패·수정·재시도를 기록한다.

완료 후 관련된 새 코드/작은 결과/보고서만 commit한다.
무관한 dirty 파일은 포함하지 않는다.
push 전에 final_checks와 git diff를 다시 확인하고,
가능하면 main에 ordinary related-files-only commit/push한 뒤
최종 remote SHA를 보고한다.

최종 응답은 다음 형식으로 짧고 명확하게 보고해.

- DONE / BLOCKED
- remote SHA
- 실제 새 inference 수 / 새 fit 수
- Robin/Peacock/Jena: LEVEL vs Mini vs Tiny 핵심 MSE
- B4: throughput / peak allocated
- 최종 판정 토큰
- 기존 LEVEL 주장에서 무엇을 유지/축소해야 하는지
- 미해결 공백 1~3개
